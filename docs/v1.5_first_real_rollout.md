## Update 2026-05-09 evening — second debugging pass

After v0 (0/4 success), six additional fixes were applied trying to
match OpenVLA's official `run_libero_eval.py` pipeline exactly:

| Fix | Source | Applied |
|---|---|---|
| Image rotation `[::-1, ::-1]` | openvla/.../libero_utils.py:56 | ✅ v2 |
| Render resolution 256, resize to 224 | openvla/run_libero_eval.py:156 | ✅ v3 |
| TF lanczos3 + JPEG round-trip resize | openvla/.../libero_utils.py:42 | ⚠️ TF crashes with libero env in same process; substituted cv2.INTER_LANCZOS4 + PIL JPEG (mean pixel diff ~13/255 vs TF ref) |
| Center crop 0.9 + resize back | openvla/.../openvla_utils.py:135-155 | ✅ v10 |
| Lowercase prompt `task_label.lower()` | openvla/.../openvla_utils.py:163 | ✅ v10 |
| Stochastic sampling for K candidates | own design | ✅ v1 |
| Gripper sign invert + binarise | openvla/.../robot_utils.py | ✅ v1 |

After all 7 corrections + tested on 5 different init states with the
exact same OpenVLA-spatial ckpt that achieved 78% in v1.4 reproduction:

| run | n_episodes | success | reward |
|---|---|---|---|
| v3 (PIL bilinear) | 4 | 0/4 | -0.018..0.000 |
| v8 (cv2 RLDS) | 4 | 0/4 | -0.018..0.000 |
| v9 (5 inits, no center crop) | 5 | 0/5 | 0.000 |
| **v10 (5 inits, all 7 fixes)** | **5** | **0/5** | **0.000** |

**v1.4 reproduction (different driver script): 78% Spatial.**

The gap is therefore not in image preprocessing or prompt formatting —
those are now byte-identical to OpenVLA's official path. Suspect
remaining differences:

1. **`processor()` int-tensor cast bug**: official `get_vla_action`
   calls `processor(...).to(DEVICE, dtype=torch.bfloat16)` which casts
   ALL tensors to bf16 — but `input_ids` are integers. This may
   silently cast / corrupt or be specially handled by HuggingFace's
   BatchEncoding.to.
2. **PrismaticImageProcessor double-application**: both rollout.py
   and the processor internally resize+crop. Official path uses PIL
   end-to-end; we round-trip Image → torch tensor → Image (via
   `_tensor_to_pil`), introducing a quantisation loop.

Either of these could OOD the visual encoder enough to break grounding.

## Decision for v1.5 paper

Given:
- v1.4 reproduction achieved 78% with the exact same ckpt
- v1.5 our adapter pipeline gets 0% on the same suite
- Each round of debugging eats ~30 minutes (5-min rollout × ~5 fixes)

**The high-ROI move is not to keep debugging the rollout differences
but to use OpenVLA's `get_vla_action` directly inside the adapter.**
Replace our `select_action`'s image transform stack with an exact-port
of `openvla_utils.get_vla_action`, treating it as the source of truth
for OpenVLA inference. Same approach for the upcoming Spirit and π0.5
adapters: copy the official inference helper, don't reimplement it.

This means:
- ✅ Keep all infrastructure: vla-lab-v1.0 image, train_dpo, train_grpo,
  reward.py, rollout.py's env loop, eval_libero.py — all proven
  correct independently
- 🔄 Refactor adapter `select_action` / `policy_logp` to call into the
  base's official inference helper rather than reimplementing image
  preprocessing
- 🔜 After refactor, re-run v10 protocol; expect 60-80% success in
  line with v1.4 baseline

This is the ~1 day of work that was deferred earlier under "option A
TF install"; with TF crashes documented and cv2 substitute identified,
the remaining engineering is the adapter-side refactor.

## What it surfaces

**0% success rate vs paper-reported 84.7% / our v1.4 reproduction 78%**
is a gap to investigate.

Three rounds of fixes applied during this run:

| Fix | Impact |
|---|---|
| Gripper sign invert (OpenVLA 0=close → LIBERO -1=open) | required, no improvement alone |
| Image 180° rotation (`img[::-1, ::-1]` vs `np.flip(img, axis=0)`) | required |
| Stochastic sampling (do_sample=True for k>=1) | enables pair diversity |
| Resolution 256 → resize 224 | tested, no improvement |

The remaining gap is most likely the **resize pipeline**:

OpenVLA's training data (RLDS) preprocessing is:

```python
img = tf.image.encode_jpeg(img)        # JPEG compress
img = tf.io.decode_image(img, ...)     # decode back
img = tf.image.resize(img, (224, 224), method="lanczos3", antialias=True)
```

That's a JPEG round-trip + lanczos3 anti-aliased resize — non-trivial
to reproduce without TensorFlow. We used PIL bilinear instead, which
likely puts inputs slightly out-of-distribution.

## Implications for v1.5 paper

1. **Limitation section**: Explicitly note our resize differs from
   OpenVLA's official RLDS preprocessing. Quote the impact on
   reproducibility.

2. **Reference numbers**: For paper table §4.2 OpenVLA SFT row, cite
   our v1.4 reproduction (78%/60%/77%/53% = 67% avg) using the
   official OpenVLA eval script, not the v1.5 rollout's 0% from this
   first run.

3. **Fix priority**: Either install TF and replicate, or accept the
   distribution shift and report only relative comparisons (DPO/GRPO
   delta from baseline within our pipeline) rather than absolute
   numbers vs paper.

4. **Smoothness reward**: With all-failed rollouts, the smoothness
   sub-signal dominates. Spread of [0.000, -0.017, -0.018, -0.018]
   shows the smoothness term distinguishes greedy (smooth) from
   sampled (slightly jerky), giving DPO a learnable ranking. Good
   sanity for the framework, weak signal for actual task progress.
