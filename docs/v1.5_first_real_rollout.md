## What it surfaces

**0% success rate vs paper-reported 84.7% / our v1.4 reproduction 78%**
is a gap to investigate.

Three rounds of fixes applied during this run:

| Fix | Impact |
|---|---|
| Gripper sign invert (OpenVLA 0=close → LIBERO -1=open) | required, no improvement alone |
| Image 180° rotation (`img[::-1, ::-1]` vs `np.flip(img, axis=0)`) | required |
| Stochastic sampling (do_sample=True for k>=1) | enables pair diversity |
| Resolution 256 → resize 224 | tested, no improvement |

The remaining gap is most likely the **resize pipeline**:

OpenVLA's training data (RLDS) preprocessing is:

```python
img = tf.image.encode_jpeg(img)        # JPEG compress
img = tf.io.decode_image(img, ...)     # decode back
img = tf.image.resize(img, (224, 224), method="lanczos3", antialias=True)
```

That's a JPEG round-trip + lanczos3 anti-aliased resize — non-trivial
to reproduce without TensorFlow. We used PIL bilinear instead, which
likely puts inputs slightly out-of-distribution.

## Implications for v1.5 paper

1. **Limitation section**: Explicitly note our resize differs from
   OpenVLA's official RLDS preprocessing. Quote the impact on
   reproducibility.

2. **Reference numbers**: For paper table §4.2 OpenVLA SFT row, cite
   our v1.4 reproduction (78%/60%/77%/53% = 67% avg) using the
   official OpenVLA eval script, not the v1.5 rollout's 0% from this
   first run.

3. **Fix priority**: Either install TF and replicate, or accept the
   distribution shift and report only relative comparisons (DPO/GRPO
   delta from baseline within our pipeline) rather than absolute
   numbers vs paper.

4. **Smoothness reward**: With all-failed rollouts, the smoothness
   sub-signal dominates. Spread of [0.000, -0.017, -0.018, -0.018]
   shows the smoothness term distinguishes greedy (smooth) from
   sampled (slightly jerky), giving DPO a learnable ranking. Good
   sanity for the framework, weak signal for actual task progress.
